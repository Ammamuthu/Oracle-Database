1. Overview

This utility finds every UNUSABLE index, index partition, index subpartition, LOB index, LOB index partition, and LOB index subpartition on one table, and rebuilds each one. It is rebuild-only — it never moves table data or partitions.

Every attempt is logged to a state table, index_rebuild_status. Once an object reaches status = 'SUCCESS', later runs skip it permanently. Anything that failed is retried automatically the next time the procedure runs. This makes the job safe to re-run if it is interrupted partway through a large table.

3. Fix required before first run

Bug in Initiate_and_Monitor.sql: the grant statements use FROM instead of TO. GRANT always takes TO; FROM is only valid on REVOKE. As written, this line errors immediately. 
-- WRONG (as currently written)
GRANT SELECT ON DBA_INDEXES FROM IMS_MM;

-- CORRECT
GRANT SELECT ON DBA_INDEXES TO IMS_MM;
GRANT SELECT ON DBA_IND_PARTITIONS TO IMS_MM;
GRANT SELECT ON DBA_IND_SUBPARTITIONS TO IMS_MM;

The REVOKE lines further down are already correct as REVOKE ... FROM IMS_MM.

Why this grant is needed: the procedure is owned by IMS_MM and reads DBA_INDEXES / DBA_IND_PARTITIONS / DBA_IND_SUBPARTITIONS. A stored procedure only honors privileges granted directly to its owner — privileges that arrive through a role such as SELECT_CATALOG_ROLE do not apply inside PL/SQL. That is why the grant/revoke wrapper exists: give IMS_MM temporary direct access, run the job, remove it again.

5.2 The local helper: run_and_log

Declared inside rebuild_indexes, so it is not a separate database object — just reusable logic that all six discovery loops below call, instead of repeating the same lines six times. For one object it does four things, in order:

  1. Check if already done. SELECT COUNT(*) ... WHERE status = 'SUCCESS'. If found, print SKIP and return immediately.
  2. Run the DDL. EXECUTE IMMEDIATE p_sql, where p_sql is the ALTER INDEX ... REBUILD [PARTITION|SUBPARTITION] statement built by the calling loop.
  3. On success — MERGE a row into index_rebuild_status with status = 'SUCCESS'. MERGE updates the row if one already exists (e.g. a retry after a prior FAILED), otherwise inserts a new one.
  4. On failure — caught by EXCEPTION WHEN OTHERS. The error text is copied into a local variable first, then MERGEd in with status = 'FAILED'. The exception is not re-raised — deliberate, so one bad index never stops the whole batch.
Why capture SQLERRM into a variable first? SQLERRM is a PL/SQL function — it only works inside PL/SQL code, not directly inside a SQL statement's VALUES/SET clause. v_err := SQLERRM; then using v_err in the MERGE is the standard workaround.

5.3 The six discovery loops

Each loop has the same shape: query the dictionary for objects in one category with status = 'UNUSABLE', then call run_and_log for each one found.

#CategorySource view(s)DDL shape
1Non-partitioned regular indexdba_indexesALTER INDEX ... REBUILD
2Non-partitioned LOB indexdba_indexes (index_type = 'LOB')ALTER INDEX ... REBUILD
3Regular index partitiondba_indexes + dba_ind_partitionsALTER INDEX ... REBUILD PARTITION x
4Regular index subpartitiondba_indexes + dba_ind_subpartitionsALTER INDEX ... REBUILD SUBPARTITION x
5LOB index partitiondba_indexes + dba_ind_partitionsALTER INDEX ... REBUILD PARTITION x
6LOB index subpartitiondba_indexes + dba_ind_subpartitionsALTER INDEX ... REBUILD SUBPARTITION x

Nothing is rebuilt unless it is actually UNUSABLE. A healthy table with no broken indexes will run the procedure and log nothing at all — that is correct, expected behavior, not a bug.

6. Known limitation: system-generated LOB indexes

Observation: Oracle's system-generated LOB indexes (named SYS_IL...$$) fail during ALTER INDEX ... REBUILD with: 
ORA-02327: cannot create index on expression with datatype LOB

This is expected Oracle behavior, not a defect in this utility. Oracle does not support rebuilding a system-generated LOB index directly with ALTER INDEX ... REBUILD. The only supported way to reorganize it is:

ALTER TABLE owner.table_name MOVE LOB(lob_column) LOB SEGMENT_NAME
  ( TABLESPACE tbs_name ... );

ALTER TABLE ... MOVE LOB rebuilds the LOB segment, and Oracle automatically maintains the associated SYS_IL...$$ index as part of that operation — it is never rebuilt directly.

What this means operationally: if run_and_log encounters one of these system LOB indexes, it catches ORA-02327, logs status = 'FAILED' with that error text, and moves on to the next object rather than stopping the batch. A FAILED row with ORA-02327 in error_message is not something to fix by rerunning this procedure — it requires a MOVE LOB operation, which is outside the scope of an index-only rebuild and should be scheduled separately with the appropriate maintenance window.

8. RUNBOOK — step-by-step execution

Follow in order. Each step lists the command, what to check before moving on, and what to do if it fails.

Step 0 — Pre-flight checklist

  • Confirm the target table name and owner: IMS_MM.MYMT_OUT_REPOSITORY
  • Confirm you have SYSDBA or equivalent access for the grant/revoke steps
  • Confirm a maintenance window / low-activity period if the table is large or heavily used, since ALTER INDEX REBUILD with PARALLEL can be I/O and CPU intensive
  • Confirm the GRANT ... FROM typo (Section 3) has been corrected in Initiate_and_Monitor.sql

Step 1 — One-time setup (skip if already done)

-- as IMS_MM or a user with CREATE TABLE / CREATE PROCEDURE on IMS_MM
@Create_Mointor_Table.sql
@INX_REBUILD_PROC.sql

Verify:

SELECT object_name, status FROM user_objects
WHERE object_name IN ('INDEX_REBUILD_STATUS','REBUILD_INDEXES');

Expect STATUS = VALID for both. If REBUILD_INDEXES shows INVALID, see Section 7 for ORA-00942 handling before continuing.

Step 2 — Capture the BEFORE status

@Pre_requesties.sql

This spools IMS_MM_MYMT_OUT_REPOSITORY_INDEX_STATUS.html. Rename it to something like status_BEFORE_<date>.html so it is not overwritten by Step 5. Note the OVERALL_UNUSABLE_COUNT_IDX value — this is what Step 4 should reduce to zero (excluding known SYS_IL...$$ cases, see Section 6).

Step 3 — Grant temporary access

-- as SYSDBA
GRANT SELECT ON DBA_INDEXES TO IMS_MM;
GRANT SELECT ON DBA_IND_PARTITIONS TO IMS_MM;
GRANT SELECT ON DBA_IND_SUBPARTITIONS TO IMS_MM;

Step 4 — Run the rebuild

SET SERVEROUTPUT ON SIZE UNLIMITED;
EXEC IMS_MM.rebuild_indexes(p_owner => 'IMS_MM', p_table => 'MYMT_OUT_REPOSITORY');

Watch the DBMS_OUTPUT stream for SKIP / RUN / OK / FAIL lines. A FAIL line does not stop the run — it will continue through the remaining objects.

Step 5 — Revoke temporary access

-- as SYSDBA
REVOKE SELECT ON DBA_INDEXES FROM IMS_MM;
REVOKE SELECT ON DBA_IND_PARTITIONS FROM IMS_MM;
REVOKE SELECT ON DBA_IND_SUBPARTITIONS FROM IMS_MM;

Step 6 — Review results in index_rebuild_status

SELECT index_name, index_kind, partition_name, subpartition_name,
       status, start_time, end_time, error_message
FROM IMS_MM.index_rebuild_status
WHERE owner = 'IMS_MM' AND table_name = 'MYMT_OUT_REPOSITORY'
ORDER BY status, index_name;
  • All rows SUCCESS? — run is complete.
  • Any FAILED with ORA-02327 and index name starting SYS_IL? — expected, see Section 6, no action via this utility.
  • Any other FAILED? — read error_message, resolve the underlying issue (tablespace space, locks, etc.), then simply rerun Step 4 — only the failed objects will be retried.

Step 7 — Capture the AFTER status

@Pre_requesties.sql

Rename the spooled file to status_AFTER_<date>.html. Compare OVERALL_UNUSABLE_COUNT_IDX against Step 2's value.

Step 8 — Close out

  • Confirm SYSDBA grants were revoked (Step 5)
  • Attach or store the BEFORE/AFTER HTML reports with the change record
  • If any non-SYS_IL objects remain FAILED, log a follow-up item with the captured error_message

9. FAQ

Is it safe to run rebuild_indexes more than once?
Yes. Anything already SUCCESS is skipped. Anything FAILED is retried. Anything newly UNUSABLE since the last run is picked up.

Does it touch table data or move partitions?
No. It only issues ALTER INDEX ... REBUILD [PARTITION|SUBPARTITION]. No MOVE statements, no data reorganization.

What if I only want to see what's broken, without fixing it yet?
Run Pre_requesties.sql on its own — it is read-only.

Why does a healthy table produce zero log rows?
Because nothing was UNUSABLE at the time — this is correct behavior, not a failure of the procedure.
